# M6.4B · Сквозная приёмка C8

Приложение из принятого `main` `5d4b773c977eadcf9ccaa002c3c41aa213b097fa`, PostgreSQL 18.6, схема `0031`. В synthetic LOCAL/TEST C8 провёл одни и те же три цепочки в Chromium desktop и narrow. В каждом прогоне Console работала со штатным owner API, Inbox и worker. Модель — FAKE v8, текст доставлял `ControlledAdapter`. В качестве доказательства доставки учитывались вызов и эффект адаптера, фактический текст, статус Outbox и строка истории адресата. Все ID ниже относятся к тестовым данным.

## Воспроизведение и граница live

Штатный CI запускает сквозной сценарий в Chromium desktop через `sh scripts/test_browser.sh`. В развёрнутой synthetic TEST-среде выбор сценария — `npm --prefix frontend run test:e2e -- intake-duration.spec.ts --grep "M6.4B follows"`. Узкий экран C8 отдельно прогнал с тем же тестом и профилем Pixel 5. Для пары настроек Q2 используется `pytest -m integration tests/test_m6_quote_delivery_postgres.py -k q2_quote_freezes`. Браузер сравнивает точный текст из транспортного адаптера с историей owner API. При независимом чтении PostgreSQL C8 связал Quote, QuoteAcceptance, ServiceOrder и ServiceSession по паре Workspace/ID каждого родителя и сверил число строк с Outbox каждого диалога.

Для live мастер должен подтвердить услуги и ограничения, режим цены и примеры расчёта на границах, длительность следующего сеанса, правила диапазона и редакцию условий предоплаты. Отдельной проверки в Telegram требуют приём сообщения адресатом, окно и права канала, receiver ACK/fence, управление HUMAN/Resume и ручная сверка прежних UNKNOWN/holds. Допуск реальных данных, фотографий и модели остаётся отдельным решением. Слоты и бронирование относятся к M7, денежные обязательства и оплата — к M8.
