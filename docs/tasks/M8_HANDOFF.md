## M8.1B — ссылка на предоплату за выбранное время

Репозиторий `Elefesys/ai-service-manager`. C7 продолжает ветку `c7/m8-1b-hosted-checkout` с документационного коммита C0. Единственный родитель этого коммита и база одного Draft PR в `main` — `e35e99a4df570d47b2af7b99ddf96e2f75eb849f`. Миграция `migrations/versions/0039_payment_checkout_attempts.py`, `down_revision = "0038"`. C3 ведёт штатный Outbox и проверку перед отправкой, C6 подключается для изолированного TEST-доступа или допуска CI. [Принятые решения](../decisions/IMPL-008-m8-pilot-payments.md) · [Путь удержания M7](../../backend/src/asm/scheduling/conversation.py) · [Обязательство M8.1A](../../backend/src/asm/client_payments/http.py).

**Первый показ.** Клиент принимает цену 4 000 ₽ с фиксированной предоплатой 500 ₽ и выбирает окно по коду. Мастер ещё не открывал карточку. Клиент получает в своём диалоге сумму, срок Hold и одну действующую ссылку на страницу оплаты. Это работает без следующей реплики клиента. Мастер видит ту же сумму и результат выдачи. Пока удержание и ссылка действуют, повтор находит прежние обязательство, попытку, ссылку и срок. Возврат со страницы оплаты показывает «Проверяем результат».

**Критерии P2**

1. Свяжи попытку с обязательством 1A, принятой версией условий, нужными Business, Client, диалогом, Session и исходными Hold/Allocation. Используй один магазин ЮKassa на бизнес и режим. Сумму и RUB бери из сохранённого обязательства. В короткой транзакции проверь срок и права, зафиксируй до первого POST устойчивый ID попытки, ключ ЮKassa, неизменный запрос или данные для его точного восстановления, отпечаток и начало окна идемпотентности. Освободи транзакцию до HTTP. У `NONE` ноль попыток и запросов. Для суммы 99 копеек при единственном способе «банковская карта» покажи причину мастеру, сохрани 99 копеек и ноль POST. [Лимиты методов](https://yookassa.ru/docs/support/payments/limits).
2. Один адаптер и контролируемый транспорт для CI. Внешний TEST использует ключ выбранного магазина, одностадийный `capture=true`, `confirmation.type=redirect` и фиксированный серверный `return_url`. Сопоставь ответ с магазином, режимом, суммой, валютой и попыткой. Для выдачи годится `confirmation_url` из аутентифицированного ответа с разрешённым HTTPS-origin. Владелец управляет записью через действующие auth/CSRF и идемпотентные команды. Остальные клиенты и бизнесы не получают ссылку. При неподтверждённых магазине или режиме выдача прекращается до внешнего POST. Полный URL доступен в защищённом пути выдачи и у адресата. В AI-контексте, общих логах, тестовых снимках и отчёте используй маскированное представление.
3. Проверь два одновременных открытия, потерю ответа сразу после внешнего POST и рестарт. Раздельно посчитай HTTP-запросы, созданные объекты и доставленные сообщения. У обычного повтора сохраняется один объект, а сообщение со ссылкой доставляется один раз. После тайм-аута или HTTP 500 сохрани неопределённый результат. ## Внешняя оплата и применение результата

**M8.1B — получение ссылки.** Один провайдер ЮKassa, один магазин на бизнес/режим; резервирование попытки и идемпотентного ключа в БД **до** внешнего POST. `PaymentSession` — попытка оплаты, не `ServiceSession` (сам визит). Один шаг (`capture=true`), redirect на страницу провайдера, фиксированный серверный return URL; данные карты принимает провайдер. Авторизованное окружение открывает ссылку, полученную из аутентифицированного ответа ожидаемого провайдера и разрешённого HTTPS-origin. Обратная страница показывает «проверяем результат» или актуальный ответ приложения; её открытие ничего не оплачивает. Новый ключ при сетевом timeout/500 не выдаётся. Не держать транзакцию открытой на время HTTP. Если API сразу вернул финальный объект без ссылки, обработать его тем же путём проверки; не делать второй POST ради URL. Повтор находит первоначальную попытку/тот же активный checkout, прежние идентификаторы и неизменный срок Hold. Новую попытку разрешать явным действием только после однозначного завершения прежней без поступления, при сохраняющихся сроке и основаниях.

До создания checkout проверить согласованную сумму по лимитам доступных способов магазина. Адресный пример для магазина с оплатой картой — обязательство на 99 копеек, понятная причина для мастера и ноль POST. Автоматически поднимать сумму до рубля нельзя. [Лимиты ЮKassa](https://yookassa.ru/docs/support/payments/limits).

Для актуального Hold связать команду с уже подтверждённым выбором времени в M7. Текущий [текст календаря](../../backend/src/asm/scheduling/conversation.py) говорит, что нужна предоплата; [проверка перед отправкой](../../migrations/versions/0037_scheduling_intents.py) повторно сверяет состояние удержания. Для ссылки использовать доверенный платёжный шаблон и отдельную проверку соответствующей попытки; не подставлять ссылку, написанную моделью, и не ослаблять эту проверку. Доставить полезную ссылку без требования, чтобы клиент написал ещё раз; не отправлять устаревшую ссылку после потери Hold или смены контекста. Если выпуск ссылки у провайдера задержался, снова проверить срок **перед отправкой**. Для неопределённого внешнего результата сохранить попытку; устаревшая или уже выданная ссылка у провайдера всё ещё может привести к платежу — обработать его, а не считать невозможным. Учесть HUMAN, состояние канала и возврат прав: новая автономная отправка не допускается, при неоднозначной доставке — UNKNOWN, не посылать снова автоматически. Обработку уже полученных денег это не останавливает.

**M8.2A — от уведомления к денежному факту.** Отдельный provider endpoint и привязанное к конкретному магазину соединение: не принимать чужой `shopId`, окружение или tenant из недоверенного тела за полномочие. Допустимые сообщения принять надёжно в Inbox/карантин, затем ответить HTTP 200; если сохранение недоступно — не подтверждать приём. Проверить источник по правилам адаптера/доверенного прокси и актуальным требованиям провайдера; для финансового эффекта получить объект через authenticated GET ожидаемого магазина. Сверить object ID, локальную попытку/неугадываемую корреляцию, получателя/merchant, тестовый режим, сумму, валюту и фактический финальный статус. Для возврата дополнительно связать с исходной проверенной оплатой и её режимом — не требовать у объекта возврата полей, существующих только у payment. `pending`, `waiting_for_capture`, флаг `paid` сам по себе, скриншот или возврат браузера не авторизуют запись.

Раннее уведомление (POST ещё не вернул ID) не терять и не связывать с клиентом по сумме: локальное намерение уже существует, позже связать с подтверждённым объектом либо оставить на разбор. При повторном событии и при устаревшем ответе хранимая денежная история не откатывается. Для обычного интернет-магазина ЮKassa перечисляет уведомление `refund.succeeded`, поэтому не полагаться на доставку отдельного webhook для каждого возможного статуса возврата: незавершённый/неизвестный результат проверяется по API. По известному ID опрашивать объект; при неизвестном ID — сверить по запросу с тем же ключом/неизменным телом в доказанном окне, списку объектов своего магазина с проверяемой корреляцией или разбору владельцем. Без надёжной связи не прикреплять перевод к чужому заказу. Ограниченная сверка (по очереди нерешённых операций, backoff, крайний срок и видимая причина) нужна независимо от webhook, после перезапуска и длительной остановки. Использовать существующий durable worker. В «выключить новые оплаты» сверка открытых платежей/возвратов остаётся разрешённой.

**M8.2B — оплаченное время.** Денежное движение вставляется один раз по (провайдер, проверенный shopId, режим, payment ID). При смене ключа того же магазина идентичность поступления сохраняется. Обновление обязательства и постановка устойчивого действия исполнения связаны атомарно; крах процесса перед проверкой календаря не теряет деньги. Отдельная команда использует доказанное достаточное покрытие по этому обязательству. В короткой транзакции под замком ресурса перечитать исходные Hold/Option/Allocation, клиента, Session, принятые условия, исходный срок, отсутствие отмены/замены, действующую занятость и границы времени M7. На `expires_at` или позже — отказ в подтверждении, даже если клиент открыл ссылку раньше или магазин отметил более раннее время оплаты. Защиту [преобразования NONE](../../migrations/versions/0034_scheduling_appointments.py) не снимать. При успехе один Appointment на **той же** Allocation; повтор/сбой после commit не перепривязывает деньги к преемнику после переноса или отмены. Подтверждение клиенту формируется после commit и проходит обычную защиту доставки.

Опоздавший платёж, избыточная/недостаточная сумма, два разных успешных provider ID или успешный онлайн-платёж после ручной отметки: сохранить проверенные движения в фактических суммах. Не списывать второй успех как технический дубль, не делать две записи, не выдавать частичную сумму за полную. Если подтверждённый проверенным магазином платёж нельзя уверенно сопоставить заказу, — видимый разбор на уровне этого магазина, без разглашения/зачёта чужому Client. Мастер видит остаток/переплату и варианты решения (согласовать другое время или явно вернуть деньги); никакого автоматического переиспользования нового Hold или возврата.

**M8.2C — ручная оплата и возврат.** Отдельная owner-команда с актуальными полномочиями, суммой, способом, причиной, источником и аудитом. «Клиент сказал, что перевёл» не является этой командой. Не выдавать ручную запись за подтверждение ЮKassa; исправление — компенсирующая запись с автором и причиной, история не стирается. Если онлайн-попытка ещё не определилась, показать владельцу риск двойного получения; известные деньги не терять. Для возврата: явное решение владельца для конкретного движения, суммы и причины; перед внешним эффектом повторно сверить полномочие/актуальность решения. Возврат на исходный платёж через провайдера; офлайн-возврат учитывается как явно подтверждённый факт соответствующего способа, не отправляется в чужую платёжную систему. Под блокировкой движения резервировать доступный остаток с учётом успешных, ожидающих и неопределённых возвратов. Учитывать и возвраты, оформленные в кабинете магазина; если доступный остаток достоверно не известен, сначала сверить его с провайдером. Крах после вызова → UNKNOWN/сверка, а не новая попытка; подтверждённый отказ освобождает резерв. После частичного/полного возврата исходное поступление сохраняется. Отмена или перенос визита сами не возвращают деньги; возврат сам не отменяет визит.

## Фискализация, кабинет и проверка магазина

**M8.3.** Принимать решение по версии BusinessLegalProfile/FiscalizationProfile: применимость, тип операции, ответственный, необходимые реквизиты/контакт, утверждённый срок, маршрут и доказательство. Минимальные стадии: требуется → ждём → зарегистрирован/подтверждён либо ошибка/просрочен. Подтверждение регистрации и передача клиенту различимы, если профиль этого требует. Если для выбранного сценария данные чека нужны уже при создании оплаты/возврата, проверить их **до** POST; нельзя вначале собрать деньги, а потом впервые выяснить, что реквизита нет. Отдельно отразить аванс/предоплату, её последующий зачёт после фактически оказанной услуги и возврат/коррекцию **там, где применимо**. Будущий зачёт можно хранить как обязанность с узким явно подтверждённым действием мастера; само наступление даты визита не означает оказанную услугу. Это не повод строить учёт всех работ или касс.

Для контролируемого сценария MANUAL_OWNER: мастер действительно формирует/передаёт чек по подтверждённой процедуре, затем прикладывает защищённый идентификатор/доказательство, а не одну галочку. Для выбранного провайдерского пути проверять результат регистрации и сопоставлять его платежу/возврату. Неполные данные, ошибка, отсутствие доказательства или просрочка → одна видимая задача в Action Center. Если деньги уже получены, не отменять их фактом фискальной ошибки, не повторять списание; при системной ошибке остановить новые оплаты по профилю. `FISCALIZATION_READY` устанавливается отдельно для конкретного бизнеса; не выводить его из успешной тестовой оплаты. Условия, под которыми допускается первый настоящий бизнес, проверяются отдельно: [OPEN-076/079](../architecture/04_OPEN_QUESTIONS.md), [runbooks RB-07 и 21](../architecture/08_PRODUCTION_DEPLOYMENT_AND_RUNBOOKS.md). Не выбирать за мастера НПД, ставки, сроки или применимость кассы.

**M8.4A.** На существующем экране заказа и календаря показать: за какую работу платят, сколько требуется, сколько подтверждено и каким источником, статус записи, срок Hold, возвраты, статус/срок чека. Один переход к требующей решения операции: поздняя оплата, неопределённый результат, переплата, ошибка чека. Обновление страницы восстанавливает фактическое состояние; мастеру не нужен SQL. В сообщениях клиента — только его суммы, время и статус. Не выводить чувствительные реквизиты другого бизнеса и внутренние данные провайдера. Модель не выбирает денежную сумму, не генерирует ссылку и не может отмечать платежи или инициировать возврат.

**Внешняя проверка, два момента.** До большой интеграции в 1B C0 выдаёт один короткий операторский порядок: подтвердить свой TEST shopId/режим по кабинету и применимой проверке адаптера, положить только TEST secret в согласованное секретное хранилище, настроить отдельный тестовый HTTPS callback при необходимости. Провайдер использует тот же API endpoint для тестовых и настоящих магазинов; одного флага в приложении недостаточно. Прежде чем создавать внешние объекты, подтвердить принадлежность тестовому магазину; на объекте платежа требовать `test=true`. Провести один разрешённый TEST create → hosted URL → тестовая оплата → GET своего объекта; сохранить маскированную квитанцию. При отсутствии внешнего callback это smoke, не доказательство доставки webhook. Не тратить деньги и не открывать production.

В 4B использовать раннее доказательство там, где граница не менялась; полный путь всё равно должен соединить штатное приложение и **настоящий тестовый магазин**: тестовый выбор Hold → сумма и ссылка → тестовая оплата/уведомление → проверенный GET → одна запись; отдельно официальный тестовый возврат и его сверка. Для выбранного профиля зафиксировать, что именно имитировала тестовая касса / какие ручные действия были показаны. Связать версии, обезличенные ID, суммы, источник события и результаты чтения; в публичном отчёте нет checkout URL/токенов, контактных/карточных данных. Если нет ключа/доступного маршрута, зафиксировать конкретный недостающий шаг: можно принять synthetic LOCAL/TEST, но `SANDBOX VERIFIED` и весь DoD с внешней проверкой **не** объявлять. Производственный договор и реальный фискальный документ остаются отдельными даже после sandbox PASS.

**Как вести этап.** Один реестр и одна активная передача. Сначала рискованные адресные проверки, потом штатный CI согласованного кандидата. Для DB-среза [PG runner](../../scripts/m4_runtime_db.py) должен действительно запустить нужную схему и проверки на PR и push/main, [browser fixture](../../scripts/m2_4_browser_fixture.py) на входе в M8.1B закрепляет `0038`; изменять допуски только когда это нужно текущему срезу. Указать фактические результаты и пропуски, не выдавать старые «160/160» за платёжные тесты. Перед слиянием C0 проверяет объём, C8 — изменённые риски по очереди, владелец разрешает слияние; после — CI фактического main. Не перезапускать неизменённые проверки без причины и не строить вторую систему приёмки. Закрывать live только по его собственным доказательствам.

**Участие владельца.** Для M8.1B и M8.4B действует [инструкция для тестового магазина](#m8-1b-test-shop). Перед live — согласовать с мастером получателя/merchant, юридический и налоговый профиль, фактические суммы и условия возврата, схему выдачи и подтверждения чека. Ни новые платные ресурсы, ни production, ни ВМ не разрешаются плановым PR. До M9 передать устойчивые ID и статусы: когда ссылка/напоминание ещё уместны, когда уже оплачено/истекло/возвращено, что требует мастера. Сами напоминания и подписка мастера на ASM в M8 не входят.
