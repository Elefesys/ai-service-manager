# AI Service Manager — правила работы исполнителей

## Приоритет пилота и решения пользователя — 2026-10-21

Пользовательский ориентир: AI-менеджер общается с клиентом, собирает нужные данные в структурированную запись и уведомляет мастера. Каждая текущая задача должна приближать проверяемый рабочий сценарий пилота.

- До реализации C0 кратко объясняет пользователю конкретный результат, пользу и необходимость для пилота, а также возможность отложить работу. Ранее не обсуждённая функция требует явного сообщения о расширении scope до начала кода; наличие её в baseline не является согласием реализовать её сейчас. Уже согласованные исправления не требуют повторного запроса на каждом шаге.
- Архитектура v0.28 — исходное проектное решение, которое может содержать ошибки и избыточность. Не подгонять реализацию под очевидно неудачный пункт. Указать проблему, предложить меньший рабочий вариант и последствия; существенное изменение зафиксировать явным решением C0/ADR и сообщить пользователю. Оригинальные импортированные файлы сохранять как исторические источники; их побайтовая сохранность не запрещает пересмотр решения.
- Не расширять заранее платформу, универсальные механизмы, матрицы состояний или диагностику ради будущих возможностей. Объём документации и число тестов не являются прогрессом функции. Сохранять короткое актуальное решение; подробные логи держать в артефактах.
- Диагностика охватывает весь известный набор сбоев: сгруппировать причины, указать затронутые проверки, фактическую ошибку, недостающий факт и исправление/блокер. После устранения общей причины проверять и положительные, и отрицательные сценарии: ранняя ошибка не должна маскировать проверяемое поведение. Отчёт только об одном падении не закрывает задачу с несколькими группами.
- Сначала целевые проверки исправления, затем полный CI согласованного кандидата. Не повторять неизменённый полный прогон ради случайного PASS. Разделять сборку, тесты, подготовку Docker/БД и ожидания; не выдавать их общую длительность за время компиляции.
- Native context продолжается в ранее выбранном варианте OWNER reconciliation + observation barrier; упрощённая версия не принята. При доказанном тупике либо дальнейшем несоразмерном разрастании без ограниченного исправления C0 останавливает цикл, фиксирует причину и переводит функцию в DEFERRED до отдельного решения пользователя о возвращении. Это не разрешение удалять данные или откатывать применённые миграции.

Изоляция клиентов/Workspace, право владельца на управление, защита от повторных отправок и достоверность результатов проверок сохраняются. Упрощение архитектуры не означает скрытое отключение этих гарантий.

## Источники и границы

Сначала читать актуальные `docs/architecture/01_ARCHITECTURE_SPEC.md`, применимые ADR, MVP Spec, Roadmap и `09_IMPLEMENTATION_PLAN.md`. Baseline v0.28 — снимок, не отменяющий более новые явно принятые файлы. До точного импорта оригиналов в Git использовать предоставленные project sources с SHA-256 из `docs/architecture/SOURCE_MANIFEST.json`; отсутствие оригиналов явно указывать. Не восстанавливать канон по пересказу этого файла.

`docs/decisions/IMPL-001-stack.md` фиксирует реализационный стек. LOCKED / OPEN / DEFERRED / REVISED — статусы решений; TODO / IN_PROGRESS / REVIEW / INTEGRATED / VERIFIED / BLOCKED — статусы задач. Нельзя смешивать их. LOCKED не делает ошибочное решение непересматриваемым: изменение требует описания проблемы, последствий и принятого решения C0/ADR согласно приоритету пилота выше. Architecture Freeze v1.0 не считается выполненным автоматически.

Критические факты определяются structured state и domain services, не LLM. Workspace — единственная tenant boundary. Runtime не SUPERUSER/BYPASSRLS/владелец tenant-таблиц. Tenant context только внутри транзакции из доверенного серверного контекста. Наличие workspace_id не разрешает доступ к чужому Client внутри Workspace. Внешние HTTP-вызовы не держат бизнес-транзакцию.

В M0 разрешены только shells, инфраструктурные роли/схемы/миграции и временные DB-пробы в asm_test. Нет будущих business tables, auth-заглушек с доступом к данным, fake paid states, очереди в памяти или пустых будущих adapters. PostgreSQL durable Jobs появляются в M2.1. Реальные данные, production credentials и платные вызовы не нужны и не разрешены автоматически.

## Выполнение и передача

Один канонический реестр: `docs/TASK_REGISTER.md`; не вести независимые дубликаты статусов по чатам. Перед стартом нужны ID, scope, зависимости, применимые ADR, repository, branch, полный base SHA, разрешённые файлы и критерии проверки. Нельзя предполагать общий диск или память между чатами.

Одна задача — отдельная ветка и checkout. Общий checkout допускает только последовательные изменения. C2/C0 назначают migration revision, predecessor и порядок интеграции. Не изменять уже применённую миграцию; не решать конфликт произвольным переименованием. C0 проверяет upgrade на чистой и предыдущей схеме.

Исполнитель возвращает commit/patch, изменённые контракты и миграции, точные команды и фактический результат, ограничения, новые OPEN-вопросы и следующий шаг. Mock/описание сценария не является PostgreSQL, live API или E2E evidence. Сборка, тесты и данные привязаны к одному проверяемому SHA.

Только C0 после проверки переводит задачу в INTEGRATED; VERIFIED требует evidence соответствующих критериев. Зависимый исполнитель начинает от принятого общего SHA, а не от непроверенного пересказа. Не force-push main, не включать production и не сливать PR с красными/неизвестными gates. Секреты не коммитить, не печатать и не включать в build context/артефакты.
